# Evaluate the workflow against its claims

Use the same selected input/action/result, assets, duration, aspect ratio and
approximate production budget for a direct Brag baseline and this workflow.
Preserve each actual first cut and one focused correction. Record concrete
failures rather than relabeling a changed brief as an equal comparison.

Choose cases matching the intended scope: an app's actual input/action/result;
a process story's intention/intermediate/result; or original physical footage
when making claims about an actual build. A CAD animation supports a design
story, not evidence that the physical object works. Missing selected footage is
a specific source gap, not permission to fabricate or record private sessions.

Assess clarity (what a new viewer understands after one muted play), factual
proof against selected sources, phone-size readability and transitions, sound
and caption usefulness, and practical effort/dependencies/retries. Retain real
human feedback separately from automatic checks and editorial interpretation.
A script pass, software playback, or a still-only review cannot stand in for
human hearing or comprehension. Avoid a single numeric score without reasons.

For portability, give an independent receiver only the package, the permitted
raw inputs and a realistic request. Do not provide the intended composition or
suspected defects. Keep outputs isolated; inspect the actual result, side
effects, missing dependencies and checks. A local clean install proves only
installation mechanics, not another being's receiving/model uptake.

Public release can describe the routes actually exercised and list untested
material/runtime combinations. Broader claims require broader evidence. Keep
private conversations, original restricted sources, account bindings and local
absolute paths out of public reports; use a brief anonymized evidence summary.
